# Decisions

Running log. Add a row when a choice is made that affects the schema, stack, hosting, or scope. Newest at the bottom.

| # | Date | Decision | Options considered | Reason |
|---|---|---|---|---|
| D1 | 2026-10-26 | Web app, installable as a PWA | Native phone app; desktop-only web app | One codebase; phone capture in the basement and laptop review at the desk; browser camera is enough |
| D2 | 2026-10-26 | Run on the Mac laptop first, then a Raspberry Pi home server | Cloud host; Pi from day one | Private, free, nothing to set up before the app exists; Pi is Phase 6 |
| D3 | 2026-10-26 | SQLite file plus a photos folder | Hosted Postgres (Supabase) | Zero infrastructure; backup is a folder copy; full data ownership |
| D4 | 2026-10-26 | Recipes: import Paprika `.paprikarecipes` export in v1; move to self-hosted Mealie (REST API) in Phase 6 | Keep Paprika link-only; AnyList via unofficial API; build recipes into the app | Paprika export format is stable and widely parsed. AnyList has no official API. Mealie is the only option with a documented API and runs on the same Pi |
| D5 | 2026-10-26 | AnyList is out of scope | Push shopping lists later | Grocery tool, not a lab tool; no official API |
| D6 | 2026-10-26 | Readings are manual entry in v1; sensor import designed for but built in Phase 6 | Sensors in Phase 1; manual only forever | Core model first; typed reading table accepts sensor rows later without a schema change |
| D7 | 2026-10-26 | Ferments are the first batch type | Mushrooms; preserves inventory | Tests the protocol snapshot and weekly-log loop with a Paprika recipe immediately. Mushrooms follow in Phase 3 |
| D8 | 2026-10-26 | Standalone app with a clean internal API | First module of a larger "Jarvis" assistant | Ship the thing that gets used in two weeks; a future assistant can read Cellar's data |
| D9 | 2026-10-26 | Name: Cellar. Repo and folder: `cellar` | Root Cellar; Labbook; Basement Lab | Short, covers grow, ferment, and preserves |
| A1 | 2026-10-26 | Single user, no login; home network only | Shared household login; multiple accounts | Nothing to build; revisit only if the Pi is exposed outside the home network |
| A2 | 2026-10-26 | Develop on a Mac laptop; target ARM64 Linux (Raspberry Pi) for the home server | Windows; Linux mini PC | Mac is in hand; Pi scoped in `cellar-brief.md` section 6 |
| D10 | 2026-10-26 | Framework: SvelteKit with `adapter-node` (resolves O1) | Next.js | Ships far less JavaScript to the phone, form actions give server routes with no client code for the one-handed capture screens, and `adapter-node` runs as a plain Node process on the Pi; Next.js adds React Server Component complexity this app does not need |
| D11 | 2026-10-26 | Database layer: Drizzle ORM with the `better-sqlite3` driver; migrations generated by `drizzle-kit` and committed | Drizzle with Node 24 built-in `node:sqlite`; Prisma; raw SQL | Drizzle is a thin typed layer whose migration files are plain readable SQL. `better-sqlite3` is the most widely used Node SQLite driver and ships prebuilt ARM64 Linux binaries, so it installs on the Pi with no compiler. `node:sqlite` avoids a native add-on but is still marked experimental |
| D12 | 2026-10-26 | Photos: `sharp` resizes each upload to a JPEG of at most 2000 px on the long side; the original is kept under `photos/originals/`. A photo's `taken_at` is the observation time in Phase 1 | No resizing in Phase 1 | `sharp` ships prebuilt ARM64 Linux binaries, so the Pi never serves full-size phone photos. Its prebuilt binaries cannot read HEIC, but iPhone Safari converts photos to JPEG on upload; a HEIC that slips through is kept as is without a resized copy. Reading EXIF dates waits until it is needed |
| D13 | 2026-10-26 | Record ids: short table prefix plus 10 random lowercase characters, e.g. `bat_7k2m9qx4hp` (no 0, 1, i, l, or o) | Prefix plus per-table counter, e.g. `bat-0004`; plain integers | Readable, shows the table at a glance, and never collides when sensor or Mealie imports add rows later. Human numbering lives in batch names such as "Ferment 004" |
| D14 | 2026-10-26 | Ferment reading kinds (resolves O2): `temp_air` (°F), `temp_substrate` (°F, brine or mash), `ph` (pH), `brix` (°Bx), `salinity` (%), `weight` (g), `specific_gravity` (SG) | Brief list 3.7 without specific gravity | Specific gravity is the standard reading for mead, wine, and kombucha. Each reading still stores its own unit |
| D15 | 2026-10-26 | Paprika import unpacked with `fflate` | Node's built-in zlib plus a hand-written zip reader; `adm-zip` | A `.paprikarecipes` file is a zip of gzipped JSON recipes. `fflate` is pure JavaScript, so nothing to compile on the Pi, and handles both layers |
| D16 | 2026-10-26 | Production runs through a small `server.js` that marks requests as plain HTTP; `npm start` runs it with a 500 MB upload limit | Set `ORIGIN` to one fixed address; turn off SvelteKit's cross-site form check | SvelteKit's Node adapter assumes HTTPS and rejected every form post from the phone. One fixed `ORIGIN` would break the other ways of reaching the app (localhost, the laptop's IP, `cellar.local`), and turning the check off would let any web page post into Cellar. If HTTPS is ever added (D2, Tailscale), drop the wrapper |
| D17 | 2026-10-26 | Repeating tasks: tapping Done stamps `done_at` and creates the next task, due the chosen interval after the day it was done. `recurrence` holds `daily`, `weekly`, or `every N days`; empty means a one-off task | One row per job with a last-done date; patterns tied to weekdays | Every check stays in the history as its own row. Counting from the day it was done means a late check never leaves a pile of missed copies. Plain words keep the CSV export readable. Seth uses airlocks, so the examples are airlock top-ups and kahm checks rather than burping |
| D18 | 2026-10-26 | Tasks are due on a date, not a time. `due_at` stores a local date such as `2026-10-27`; `done_at` keeps the full timestamp | Optional time of day; time always | Matches daily and weekly chores, and Today simply shows everything due today or earlier. Less to tap on a phone |
| D19 | 2026-10-26 | Protocols can carry an optional task list in `body_json` (title, first day, repeat, optional last day). It is copied into the batch snapshot with the rest of the protocol, and the tasks are created when the batch is created | Tasks added by hand only | "Check airlock water weekly until day 28" is part of a method and should come with it. The list is optional, so protocols and batches saved before Phase 2 load unchanged |
| D20 | 2026-10-26 | No phone push reminders. The Today screen is the reminder | Web push notifications | Web push requires HTTPS, and Cellar runs on plain HTTP on the home network (D16). Revisit if HTTPS arrives with the Pi (D2) |
| D21 | 2026-10-26 | `task` gains two nullable columns: `repeat_until` (last date a repeat may land on) and `previous_task_id` (the task whose Done created this one). Open tasks on a finished batch are hidden, not deleted | Encode the stop day in the `recurrence` text; delete open tasks when a batch finishes | A separate stop date keeps `recurrence` simple and lets "weekly until day 28" end on its own. The back link lets Undo remove the copy a mistaken Done made. Hiding instead of deleting means reopening a batch brings its tasks back |
| D22 | 2026-10-26 | Contamination gets its own `contamination` table, one row per event on an observation: type (`trich`, `cobweb`, `bacterial`, `black_mold`, `other_mold`, `pests`, `other`), severity (`spot`, `patch`, `widespread`), and action taken (`watching`, `spot_treated`, `cut_out`, `tossed`). The note and photos come from the observation | Three columns on the observation; a contamination flag plus a free-text note | Typed rows can be counted and compared across grows ("how often did trich show up"), get their own CSV, and one check-in can hold more than one event |
| D23 | 2026-10-26 | Flushes are a nullable `flush` number on the observation, set on harvest check-ins (the ones with a harvest weight). The next number is filled in and can be changed. The batch page totals each flush, and the finish screen fills in total yield in grams, still editable | A `flush` table with its own start and harvest dates; no numbers, counted by order | A harvest is already a check-in with a weight and photos, so one number is all that is missing. No second record to open, close, or keep in sync |
| D24 | 2026-10-26 | Mushroom reading kinds: `temp_air` (°F), `temp_substrate` (°F, shown as substrate temp), `rh` (%), `co2` (ppm), `light_hours` (h), `weight` (g, for weighing a block), and a new `harvest_weight` (g) that only the harvest part of the check-in offers | Reuse `weight` for harvests; also add a dry substrate weight for biological efficiency | A separate kind means harvests never mix with block weighings on charts or in the yield total. Biological efficiency can be added later from the same rows |
| D25 | 2026-10-26 | One protocol form for every batch type, with the type chosen when the protocol is created and fixed after. A mushroom protocol has materials, tek steps, a task list, and target ranges that apply to all phases or to one phase (`targets[].phase`; a phase target wins over an all-phases one). Paprika import stays ferment-only | One target set for the whole grow; a separate mushroom form | Colonization and fruiting want very different conditions, so the check-in should compare against the current phase. One form keeps ferments and mushrooms in step. Old targets have no phase and keep applying everywhere |
| D26 | 2026-10-26 | A protocol task can belong to a phase (`tasks[].phase`). It is created when the batch enters that phase, with its first day counted from that day, and its open copy is removed when the batch leaves the phase. `task` gains a nullable `phase` column, and repeats carry it. Done copies stay in the history | Day-based tasks only; offer the phase's tasks as tick boxes on a phase change | Colonization speed varies, so "mist and fan daily" should follow the grow, not the calendar, and come back on its own for each flush (fruiting, harvest, fruiting again) |
| D27 | 2026-10-26 | Mushroom phases are a fixed list (spawn, colonization, fruiting setup, fruiting, harvest, cleanup), picked with big buttons on the check-in and batch form and stored as text. Phase tasks and phase targets are offered only for batch types with a fixed list, which is mushrooms for now; ferments keep the free text box | Keep the free text box with suggestions | One thumb, no typing, and the names always match the phase tasks and targets |
| D28 | 2026-10-27 | A preserve protocol has typed processing fields in `body_json.processing`: method (`water_bath`, `pressure`, `steam`, `fridge`, `freezer`, `dehydrate`), headspace in inches, and a list of jar sizes, each with its minutes and psi. Times are entered already adjusted for altitude; the form reminds that Stevens Point is about 1,100 ft but the app never computes an adjustment | One jar size and one time; processing details in the steps text only | Pints and quarts of the same recipe process for different times, and the canning-day screen should show the right number big. Altitude rules differ by recipe and by canner gauge, so the safe source is the tested recipe, not arithmetic in the app. The fields are optional, so ferment and mushroom protocols load unchanged |
| D29 | 2026-10-27 | Finished jars go on the shelf as inventory items, one row per jar size (or per shelf). The finish screen offers "Add to shelf" rows, prefilled from the protocol's jar sizes, and the batch page has an "Add to shelf" button for later. Each item keeps its `batch_id` | One item per batch; one item per jar | Pints and quarts are used and counted separately, and a jar-by-jar list would be too long to tap through on a phone |
| D30 | 2026-10-27 | A preserve protocol carries an optional shelf life in months (`body_json.shelfLifeMonths`). It prefills each item's use-by from the packed date, and the use-by can be changed per item. The use-by view flags items past their date and items within 2 months of it as "soon" | Flag within 1 month; use-by typed per item only | Most canned goods carry a 12 to 18 month guideline per recipe, so the protocol is the right place for it. Two months is time enough to plan to eat a jar before it passes |
| D31 | 2026-10-27 | A one-tap "Used one" lowers an item's quantity by 1, with Undo. Status follows the quantity: `gone` at 0, `low` at 2 or fewer, `in_stock` above. No usage history is kept and no table is added | A dated row per use in a new table; counts typed by hand | Fastest on the phone in the basement, and the existing `inventory_item` table already holds everything it needs |
| D32 | 2026-10-27 | Any batch can add items to the shelf (kraut into the fridge, dried oysters), not only preserves. Items not made in-house (store-bought, gifts) are added by hand with no batch | Preserve batches only, with or without outside items | The shelf should match what is really there, wherever it came from. `inventory_item.batch_id` is already nullable for this |
| D33 | 2026-10-27 | A new preserve protocol starts with a day 1 task "Check seals, remove rings, label", which can be edited or removed like any protocol task. Preserves add no new reading kinds; air temp is offered as for every type | Also log canner psi and sealed or unsealed jar counts; no default task | The seal check is the one step every canning batch shares. Psi is set by the canner weight, so logging it adds taps without adding information |
| D34 | 2026-10-27 | Preserve phases are a fixed list (prep, processing, cooling, stored) with the same big buttons as grows (D27), so preserves also get phase tasks and phase targets | Keep the free text box | One thumb on canning day, and phase names stay consistent across batches |
| D35 | 2026-10-27 | A hydroponic batch is one tower run: one planting of the whole tower, from filling it to tearing it down. The tower is linked to the batch as equipment, like any other gear. Crops are listed in the notes | One batch per crop; the tower as a space with a batch per crop | The tank is shared, so pH, EC, and water level belong to the whole tower and are logged once per check-in. One batch per crop would mean logging the same tank readings on every crop |
| D36 | 2026-10-27 | Tower reading kinds: `ph`, `ec` (mS/cm), `water_level` (in), `temp_air` (°F), `light_hours` (h), `height` (in), water temp (`temp_substrate`, °F, shown as water temp), and `harvest_weight` (g) on cut days. Harvests are numbered (Harvest 1, 2, 3) with the same `observation.flush` column as mushroom flushes (D23), and their total fills in the yield on the finish screen | Brief list plus water temp, no harvests; brief list only | A warm tank grows root rot, so water temp is worth a number. Cut-and-come-again harvests behave like flushes, so the existing column and totals carry them with no schema change |
| D37 | 2026-10-27 | Seedling reading kinds: `temp_air` (°F), `rh` (%), `light_hours` (h), `height` (in), soil temp (`temp_substrate`, °F, shown as soil temp), and two new counts, `seeds_sown` and `seeds_sprouted` (unit `seeds`). Germination rate is the latest sprouted count over the latest sown count, worked out when shown, never stored. Counts take no target range | Counts without soil temp; brief list only, germination in the note | Heat mat temperature drives pepper germination. Counts as typed readings chart and compare like any other reading, and need no new column. A seedling batch is one sowing: a tray or flat of one variety |
| D38 | 2026-10-27 | Towers and seedlings join `FIXED_PHASES` with big phase buttons (D27), so they also get phase tasks and phase targets. Tower: germination, seedling, vegetative, flowering, harvest. Seedling: sown, germinated, true leaves, potted up, hardening off, transplanted | Seedlings only; neither | One thumb, and phase names match across batches so the comparison can line them up |
| D39 | 2026-10-27 | The comparison lines batches up on days since start (Day 0) | Calendar date; days into each phase | A March run and an October run sit on the same axis, and day numbers are already how every batch page counts |
| D40 | 2026-10-27 | Any batches of the same type can be compared, two to four at a time. Batches of the same protocol (any version) are listed first and picked by default | Same protocol only; any batches at all; exactly two; any number | Two pepper varieties from different protocols are still worth comparing. Four overlaid lines are the most a phone chart can show clearly |
| D41 | 2026-10-27 | The comparison shows overlaid reading charts (one line per batch), outcome and yield side by side (status, days run, yield, rating, harvest total or germination rate, summary, next time), and a phase timeline (the day each batch first checked in at each phase). Photos by day are left for later | All four sections, including photos by day; charts and outcome only | Charts answer "did conditions differ", outcome "which turned out better", and the timeline "which was faster". Photos by day means loading many images over basement Wi-Fi, and each batch page already has its photos |
| D42 | 2026-10-27 | Equipment can be added from a photo. Claude (Anthropic's vision API) reads the photo and fills in what it finds: name, brand, model, kind, count, and sizes. The photo is sent to Anthropic only when "Add from photo" is used; check-in photos never leave the house. Without internet or an API key, the same screen opens with a blank form | Barcode scan with an outside lookup service; a local model on the laptop or Pi | Claude can read labels and printed sizes and knows common products by model number. Barcodes miss buckets, jars, and DIY gear and still need an outside service. A local model can only say "bucket" and is heavy for a Pi |
| D43 | 2026-10-27 | One photo can add several items. A review screen shows a card per item found, each ticked; Seth unticks what he does not want, fixes anything, and saves. Identical items (12 quart jars) become one equipment row with a count | One item per photo | A shelf goes in with one photo. One row per jar would bury the equipment list |
| D44 | 2026-10-27 | Sizes are filled in when printed on the item or known for that model. Sizes eyeballed from the picture are marked as estimates and must be confirmed or fixed before saving. Every recognized size is saved with its unit and where it came from (label, known, estimate, or typed by Seth) | Only printed or known sizes, never guesses; no sizes at all | Bucket and crock sizes are rarely printed but a good guess is useful, as long as a guess never quietly becomes a fact |
| D45 | 2026-10-27 | The photo stays with the equipment it added and shows on the equipment page. Equipment pages can also take photos added by hand | Use the photo only for recognition, then discard it | A picture is the quickest way to know which crock is "Crock 2". Needs a small schema change |
| D46 | 2026-10-27 | Equipment photos live in a new `equipment_photo` table (id, equipment_id, path, original_path, caption, taken_at), files on disk like check-in photos. One photo file can sit on several items; it is deleted only when the last item lets go of it | Make `photo.observation_id` nullable and add `equipment_id` to it | A new table leaves every check-in photo query alone. Changing a NOT NULL column in SQLite means rebuilding the table |
| D47 | 2026-10-27 | Photo reading uses `claude-opus-5-5` by default (about 5 to 10 cents a photo), changeable with `CELLAR_VISION_MODEL`. The API key goes in a `.env` file next to the app, loaded at startup, never stored in the database or exports. Claude answers in a fixed JSON shape that the server checks before showing it. Sizes are stored in `specs_json` as `capacity_qt: 23` with `capacity_qt_source: known`, plus `count` and `brand`, so they edit in the specs box like any other spec | A cheaper model; storing the key in Settings; new columns for sizes | The best model reads labels most reliably and the cost per photo is small. A key in the database would end up in every backup and export. The specs box already uses the name_unit style, so no schema change |
| D48 | 2026-10-27 | The old Phase 6 is split and a look and feel phase goes first: Phase 6 look and feel, Phase 7 always on (background service, Pi, backups), Phase 8 sensors and Mealie. Where earlier rows say "Phase 6" for the Pi, backups, sensors, or Mealie, read Phases 7 and 8 | Pi first, then looks; looks as the last phase | Looks is all software and can start now, and a pleasant app is one that gets used. The Pi waits on buying hardware (O3), and sensors and Mealie wait on O4 and a Mealie install |
| D49 | 2026-10-27 | The look is "Root cellar": warm paper background, the phone's serif for headings, an olive accent, and an earthy color and icon per batch type. From the photo-first idea: Today shows active batches as a two-column photo grid, and the Batches list uses compact rows with a small photo. A batch with no photo shows its type icon. Screens use named colors from `layout.css` only; a lint check refuses raw Tailwind colors | Lab notebook (white, teal, monospace numbers); Field kit (bold photo tiles) | Easy on the eyes in a dim basement and suits a pantry notebook. Photos are the quickest way to recognize a batch |
| D50 | 2026-10-27 | Dark mode follows the phone, with Auto / Light / Dark in Settings. The choice is a cookie on that phone, so the server draws the right colors on first paint | Follow the phone only; always dark | Some evenings the phone is dark but the basement light is bright, or the other way round |
| D51 | 2026-10-27 | Icons come from Tabler (`@tabler/icons-svelte-runes`), bundled with the app, one import per icon. Fonts are the phone's own: system sans, system serif for headings | Lucide; no icons; a bundled custom font | Tabler has mushroom, seedling, and bottle icons. Nothing downloads, so it works offline and on the Pi |
| D52 | 2026-10-27 | No service worker or cached offline screen for now. Instead: the check-in screen keeps the note and readings on the phone until the save goes through (photos are not kept across a reload), a save that cannot reach Cellar stays on the form with everything filled in, and the error page explains Wi-Fi drops in plain words | A service worker that caches the app and an offline page | Phone browsers only run service workers over HTTPS or on localhost, and Cellar is plain HTTP on the home network (D16), so it would never run on the phone. Revisit with HTTPS in Phase 7 |
